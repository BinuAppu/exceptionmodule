# Exception Management Platform

> **Status: proposed architecture; not production-approved.** The documentation in `docs/` is a design and acceptance specification. Local Docker startup has been exercised, but the repository does not provide production acceptance or deployment evidence.

The target platform is a React/Vite browser client backed by a FastAPI Python API. SQLAlchemy provides the data-access layer, with PostgreSQL required for production and SQLite permitted only for isolated local tests. It uses opaque server-side sessions, runtime-configurable OpenID Connect or SAML SSO, a separately controlled local break-glass administrator, transactional workflow/outbox processing, quarantined file handling with a ClamAV integration point, and advisory-only Azure OpenAI analysis.

## Local Docker quick start

On a fresh Linux, macOS, Windows/WSL, or other Docker-capable host, install Docker, Compose, Bash, OpenSSL, and `curl`, then run:

```bash
cd /path/to/exception
chmod +x install.sh
./install.sh
```

The installer creates a unique local `.env` without replacing an existing one, builds the frontend and backend, starts PostgreSQL, ClamAV, the API, and the worker, and waits for readiness. Open **http://localhost:8000**, select **Break-glass access**, and use the credentials generated by the installer. After signing in, an administrator can configure OIDC or SAML at **http://localhost:8000/admin/sso**.

See [`steps-to-install.txt`](steps-to-install.txt) for prerequisites, remote access, manual configuration, credential cleanup, troubleshooting, and destructive volume operations.

## Single sign-on

Administrators configure one active workforce identity provider at **Administration → Single sign-on** (`/admin/sso`):

- **OpenID Connect:** Authorization Code flow with PKCE, state, nonce, browser binding, exact issuer/client/tenant checks, and optional just-in-time requester provisioning.
- **SAML 2.0:** service-provider-initiated flow with signed AuthnRequests/assertions, a pinned IdP certificate, RelayState transaction binding, SP metadata, and strict destination/audience/recipient/replay checks.

Client secrets and signing private keys are write-only and encrypted at rest. Use **Test configuration** before enabling sign-in. Keep the local break-glass credential available until an independent test sign-in and account-disable test have succeeded.

## Intended source ownership

These paths define intended source ownership. Source files may be present, but their presence is not implementation, integration, or acceptance evidence:

- `backend/app/api/routes/` — HTTP boundary and authorization dependencies
- `backend/app/core/` — settings, security, logging, and shared policy
- `backend/app/db/` — SQLAlchemy session/transaction management
- `backend/app/models/` — normalized relational model
- `backend/app/schemas/` — request/response and AI output schemas
- `backend/app/services/` — business workflow and authorization rules
- `backend/app/integrations/` — Entra ID, email, object storage, ClamAV, and Azure OpenAI adapters
- `backend/app/workers/` — outbox consumers and retry/dead-letter processing
- `backend/alembic/versions/` — PostgreSQL schema migrations
- `backend/tests/` — unit, integration, security, contract, and workflow tests
- `frontend/src/` — React/Vite presentation and same-origin API client
- `.github/workflows/` — build, test, scan, migration, and evidence automation
- `storage/attachments/`, `storage/backups/`, `storage/exports/` — local runtime data only; never source control or production evidence storage

See `docs/06-acceptance-and-production-gates.md` for the evidence required before any production approval.
